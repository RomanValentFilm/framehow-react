# FRAMEHOW — AUDIT OF SYNC AND DATA
### 19 August 2026 · against v4.9.064 (deployed) / v4.9.065 (working copy)

Scope: the sync engine, the store, local persistence, the server routes, the schema
and the migrations. Not the UI, PDF, camera or exports.

Everything below was read in the code. Where something is reasoned rather than
observed, it says so.

---

## HOW TO READ THIS

Findings are ranked by one question: **can this lose someone's work without
saying anything?** That is the only failure that matters on a shoot, because it
is the only one nobody notices until it is too late to redo.

- **EATS WORK SILENTLY** — work disappears, no message, often no way back
- **VISIBLE BUG** — wrong, but you can see it and work around it
- **STRUCTURAL RISK** — fine today, bad the once it isn't
- **LOOSE END** — tidy-up

---

# THE THREE TO FIX FIRST

## 1. Last night's fix did not cover settings or deletions
**EATS WORK SILENTLY** · `backend/src/routes/projects.ts:1196`, `:1191`

#313 put frames, versions, images and drawings on one clock — the server's. Two
tables were left behind, and both are on the same delta path:

- `project_settings.changed_at` — the **device's** clock
- `project_deletions.deleted_at` — the **device's** clock

Both are filtered against `since`, which is a **server** time. Exactly the
comparison #313 existed to abolish.

**What happens to you.** You rename a needs category on the iPad on Monday,
offline. The iPad reconnects on Wednesday. The desktop last pulled on Tuesday.
The rename arrives stamped Monday, the desktop asks for everything since
Tuesday, and Monday is not after Tuesday — so it is never handed over. Not late.
Invisible, permanently, because that watermark only climbs.

The deletion case is worse. Delete a frame offline; the tombstone never reaches
the other device; the frame lives on there for ever. And every edit made to that
frame afterwards is thrown away in silence by the server's "dead stay dead"
filter (`projects.ts:338-363`) — the push returns 200 and writes nothing.
**"Deleting is final" fails in both directions at once.**

This also fires with no offline involved at all, on any device whose clock runs
a minute slow.

There is no arrival-time column on either table to filter on instead, so this
needs a schema change, not a one-line fix.

## 2. Two devices make the same id for different things
**EATS WORK SILENTLY** · three places, one mechanism

Settings are stored on the server keyed by `(project, kind, item_id)`
(`migrations/0021`). Two different objects sharing an `item_id` are literally
one row. And three kinds of id are counted **per device**, starting at 1:

| what | where | id |
|---|---|---|
| shooting order | `src/lib/sortOrder.ts:1417`, `:1451` | `sort_1`, `sort_2`… |
| setup | `src/lib/setups.ts:183`, `:404` | `setup_1`, `setup_2`… |
| frame group | `src/lib/groups.ts:444` | `1`, `2`… |

**What happens to you.** You make your first shooting order on the desk. Your
gaffer makes their first one on the iPad, offline. Both are `sort_1`. They meet
as one row, later wins, and one order — its arrangement, its breaks, its bracket
tree — is gone. The list is still called SHOOTING ORDER 1, so nothing looks
wrong.

**Setups are worse than loss — they mislabel.** The whole setup palette travels
as a *single* item (`projectSettings.ts:86`), so two devices each adding a setup
lose one outright regardless of ids. And frames carry `setup_1` on them. Device A
makes `setup_1` = DAY and tags 20 frames; device B makes `setup_1` = NIGHT and
tags 12. After the merge, half your storyboard is colour-coded with a setup that
was never applied to it. That is wrong shooting data, not a missing list.

Frames, versions, images, drawings and needs items are all safe — they use real
unique ids. Only these three are counted.

Two more things make it compound: nothing ever recomputes the counters after a
merge (contrast `accountFlow.ts:4233`, where frame numbering *is* recomputed), so
a device can hold four orders with its counter back at 1 and collide with itself.
And breaks use `brk_${Date.now()}` with no device part (`sortOrder.ts:2422`) —
same shape of mistake, much smaller odds.

**Fix:** give these three a device-unique id (`getDeviceId()` already exists),
and reconcile the counters to `max(existing)+1` after every merge.

## 3. The old whole-project blob still overwrites the new per-item settings
**EATS WORK SILENTLY** · `src/lib/accountFlow.ts:2848-2912`, then `:2917`

This is the vanishing break, and it is worse than I guessed last night.

On a pull, the store is rebuilt from the project's **metadata blob** first —
groups, setups, needs, sort orders, story-flow breaks, all replaced wholesale
(`:2868`–`:2906`). *Then* `applySettingsToStore` runs (`:2917`), which reads the
store fresh — by which time it is already looking at the server's copy.

So the protection that says "my copy is newer and unsent, don't overwrite it"
can only decline to write. Nothing puts the local value back. **On the pull path
it does nothing at all.**

Same for the frame arrangement (`:2848`): the server's order is installed, and
the guard then declines to apply the local one. "The later arrangement wins
whole" fails in the direction that loses yours.

Three things make it easy to hit:

- the change usually isn't stamped yet — stamping happens on the autosave, which
  waits two seconds *and defers itself while a pull is running*
- a settings-only change doesn't hold the pull back (that was deliberate, #305)
  and doesn't trigger a push of its own either
- after the pull, `clearDirtyState()` wipes the record that anything was pending

Named plainly: **every settings item is pushed twice** — as its own row *and*
inside the blob. Migration `0021` exists to end the blob. On the apply path the
blob still wins.

# ALSO EATS WORK

## 4. A pull that fails erases the record of unsent work
**EATS WORK SILENTLY** · `src/lib/accountFlow.ts:4710`

`try { adoptFingerprintsFromStore(); } catch {}` runs even when the pull died
*before touching the store* — a timeout, a dropped connection. It then records
every frame on screen, including ones holding unsent work, as already matching
the server. The next push finds nothing to send, reports success, and clears the
dirty list. A drawing made just before a dropped connection is never uploaded,
and the next pull overwrites it.

Should only run when the store was actually rebuilt.

## 5. Two different answers to "did this frame change?"
**EATS WORK SILENTLY** · `changeStamps.ts:32-42` vs `accountFlow.ts:4052-4085`

One definition includes the frame's versions; the other deliberately doesn't.
The pull uses the first to decide *which frames are dirty* and the second to
decide *who wins*. A frame that's dirty only because you made a new LOOK on it
has no change time by the second definition, so it loses, and its unsent version
is rebuilt out of existence from the cloud copy.

## 6. Tombstones don't survive a restart, and leak into the next project
**EATS WORK SILENTLY** · `accountFlow.ts:4099`, `:2281`

Pending deletions live only in memory — not in the local snapshot. Delete a frame
offline, close the app before it syncs: the frame is gone locally *and* the
record of the deletion is gone, so the next pull brings it back. Nothing objects,
because the safety check only guards frames going missing, never frames
returning.

They're also not cleared on a project switch, so unsent deletions from project A
ride into project B's push.

## 7. Restore can empty a project and fail to refill it
**EATS WORK SILENTLY** · `backend/src/routes/projects.ts:1021`, `:1075`

Restoring deletes everything in one transaction and rebuilds in a second. If the
second fails — oversized payload, timeout, CPU limit — the project is left empty
with no rollback. The pre-restore snapshot is the only way back, and you'd have
to know to look.

Related: a restore writes no tombstones and no change times, so any device still
holding the old frames pushes them back and wins — quietly undoing the restore
frame by frame.

# STRUCTURAL

## 8. A clean database cannot be built from the migrations
**STRUCTURAL RISK**

Two independent reasons:

- **It stops at `0019`.** `0018` creates `frame_conflicts` already containing
  three columns that `0019` then tries to add. On an empty database that's three
  `duplicate column` errors and wrangler halts. `migrations_dir` in
  `wrangler.toml` is decorative.
- **Six columns exist in no migration at all:** `projects.metadata`,
  `frames.version_label`, `frames.strip_labels`, `frames.hidden`,
  `versions.hidden`, `versions.starred`. On a migrations-only database the very
  first project load dies on `no such column: metadata`.

And a **seventh** that isn't even in the drift file: `projects.orientation`, used
by `analytics.ts:650`. Either production has a column nobody wrote down, or that
admin page has been returning 500 every time it's opened.

Nothing is broken today. It becomes catastrophic exactly once — the day you need
a second environment, or the database back.

## 9. The snapshot on the push path is unbounded and unguarded
**STRUCTURAL RISK** · `backend/src/routes/projects.ts:1772-1794`, called at `:476`

Every push may serialise the entire project — every drawing's JSON included —
into a single database value. Drawings are capped at 1 MB each; there is no cap
on the total. D1 has a hard ceiling on one value. A project with a handful of
real drawings will cross it, and the call is awaited without a guard, so
`POST /sync` then throws before writing anything. **For ever, on every retry.**
The project becomes permanently unsyncable with a bare 500.

## 10. Every image load scans every image row
**STRUCTURAL RISK** · `backend/src/routes/upload.ts:120`

`WHERE i.r2_key = ?` runs on every single image fetch, and there is no index on
`r2_key`. One line, largest payoff in the file.

## 11. The needs defaults are one shared object, edited in place
**EATS WORK SILENTLY, across projects** · `store/state.ts:608`, `needs.ts:326-552`

Renaming a needs category edits the *default* object, not a copy. Start From
Scratch after that, and the new project opens holding the previous project's
renamed categories — and pushes them to the server as though you'd typed them
there.

## 12. Nothing ever deletes tombstones, and some snapshots are never thinned
**STRUCTURAL RISK**

`project_deletions` is documented as "cleaned up after 30 days by cron". Nothing
anywhere deletes from it. It grows for the life of the account and is scanned
twice per push. And after 30 days the pull stops delivering rows that are still
in the table, so "deleted while you were away" becomes indistinguishable from
"never existed".

Separately, `pre_restore` and `offline` snapshots are kept unconditionally for
48 h and one is created every time the restore list is opened. Open it fifty
times in a day and the database holds fifty full copies of the project.

## 13. A fast clock can make every other device go deaf
**VISIBLE BUG** · `backend/src/routes/projects.ts:1518`, `:1631`

`projects.updated_at` is stored as `MAX(what the device said, server now)`. A
device ten minutes fast pushes once, and every other device sets its "I am up to
date as of" ten minutes into the future — then reports nothing new for ten real
minutes no matter what lands. Related to #314 and an argument for doing it.

## 14. Deleted frames leave most of themselves behind
**STRUCTURAL RISK** · `src/lib/actions.ts:371-375`

Deleting a frame clears four of its thirteen entries. Left behind for the life of
the project: its sketch and reference strips — **which hold base64 images** — its
needs, its notes, and more. All of it written into every local snapshot, for
ever. The app already has a "this iPad has no room, your changes are NOT saved"
path; this leak feeds it directly. There are two delete paths and they clean up
two different incomplete subsets.

## 15. Change detection counts strokes and reads 40 characters of an image
**STRUCTURAL RISK** · `accountFlow.ts:4052-4085`, `changeStamps.ts:32-51`

A drawing is summarised by *how many* strokes it has, so erasing one and drawing
another reads as no change. A photo is summarised by the first 40 characters of
its data — which for two PNGs of the same size, or two JPEGs from the same
camera, are identical. Reasoned, not measured: 40 base64 characters is 30 bytes,
and image formats spend their first 30 bytes on fixed headers.

Concretely: retake a photo on the same frame while offline, and the frame may
read as unchanged and never upload — then be replaced by the old one on the next
pull.

## 16. Breaks are pinned to a position, not to a frame
**STRUCTURAL RISK** · `store/state.ts:379`

A break remembers "I am at slot 4". Frames added or removed *on the other device*
shift everything under it without moving the break. LUNCH quietly slides two
frames earlier after a sync. Anchoring a break to the frame it follows removes
the whole class.

## 17. Boot order: an empty store is read as "nothing to remember"
**EATS WORK SILENTLY, conditionally** · `currentProject.ts:615`, `init.ts:1298`

Autosave starts before the local snapshot is restored, and the restore waits on a
network call that has **no timeout**. In that window the store is empty, and an
empty store with no project name is read as "there is nothing here" — and the
local snapshot is deleted.

*Speculative:* I could not prove a guaranteed store write in that window. But
rotating the iPad, or the keyboard resizing, is enough — and a hanging network
start is exactly the moment a person fidgets with the device.

# LOOSE ENDS

- **Dead merge strategy** — `mergeFrames` and `framesMatch` (`accountFlow.ts:4193-4271`), ~80 lines implementing a rule that contradicts the current ones and cannot run.
- **The old frame picker** — `rejected_frames` is documented ALWAYS EMPTY since #303, so ~130 lines of picker plus its server branches are reachable only by devices on pre-#303 builds. `frame_conflicts` is read on every heartbeat and written by nothing.
- **`frames.changed_offline`** — still selected, still written, read by nobody.
- **`layoutMode`** in the store — zero readers anywhere.
- **`lastPdfName` survives a new project** — so a fresh project exports named after the previous project's PDF.
- **`safePull`'s guard doesn't hold** — the inner pull clears the in-flight flag in its own `finally`, so the window it exists to close is open anyway.
- **Every push downloads the whole project back** (`projects.ts:558`) even though the pusher has it and delta pull exists.
- **Every push scans all the user's other projects** to compare against a storage cap.
- **PDF-adjust data keyed `'local'`** for any unsaved project, so two unsaved projects share and then steal each other's layout.
- **Admin analytics takes its token as a URL parameter**, which puts it in logs.
- **`SYNC-BEHAVIOUR-LIST.md`** still describes the frame picker as existing.

# WHAT THIS ADDS UP TO

Three separate faults last night were the same mistake about time. Three more in
this audit are the same mistake about identity — two devices counting from 1 and
meeting. And three more are the same mistake about *layers*: an old whole-project
blob and a new per-item system both still live, with the old one winning.

None of these are careless. Each was right when it was written, and was left
standing when the thing beside it changed. That is what an audit is for.

The pattern worth taking from it: **when a rule moves, the old holder of that
rule has to be removed, not just bypassed.** The metadata blob, the frame picker,
the two definitions of "changed" — all three are old holders still in the room.
